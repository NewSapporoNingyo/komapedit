# 使用 AI 编程工具开发 komapedit

[English](ai-dev.md) · [人工开发者指南](dev_zhcn.md) · [供 AI 工具阅读的仓库规范](../AGENTS.md) · [开发进度待办事项](../TODO.md)

本文档面向使用 AI 编程工具开发 komapedit 的人，说明如何准备任务、监督工具、审查修改，以及判断结果是否可以安全接受。它不是提示词合集，也不应整篇复制给 AI 工具。

AI 工具本身应阅读包含详细仓库规则的 [`AGENTS.md`](../AGENTS.md)。操作工具的人仍然需要对目标、范围、技术决策、验证和最终验收负责。

## 明确区分人与工具的职责

操作者需要决定：

- 哪个问题值得解决，预期结果是什么；
- 哪些文件、组件、用户和数据属于本次范围；
- 哪些现有行为必须保持不变；
- 哪些证据能够证明任务完成；
- 是否接受架构、ABI、依赖或产品策略方面的变化。

AI 工具可以帮助检查仓库、追踪行为、提出方案、修改文件和运行检查。应把它的结论视为需要证据支持的建议，而不是因为表述自信就自动成为正确决定。

各项目文档用途不同：

- [`README_zhcn.md`](README_zhcn.md)：当前用户行为与限制；
- [`TODO.md`](../TODO.md)：实现状态与计划；
- [`dev_zhcn.md`](dev_zhcn.md)：开发者所需的构建、架构、编码和测试信息；
- [`AGENTS.md`](../AGENTS.md)：AI 工具必须遵守的详细规则。

## 在要求修改代码前做好准备

首先检查工作区，记录不能覆盖的已有修改。处理缺陷时尽量先复现；处理性能问题时先记录基线；涉及编辑或保存功能时，应使用已备份的线路文件或受版本控制的测试固件。

为自己写一份简短的任务说明，回答以下问题：

1. 当前缺少什么，或哪里存在错误？
2. 修改后，用户或开发者应观察到什么结果？
3. 哪个组件可能持有这项行为？
4. 哪些行为不能改变？
5. 将使用哪些测试、比较或手工检查？
6. 哪些工作明确不在本次范围内？

这是一份帮助操作者做决定的检查清单，不是固定的提示词格式。发给工具的文字可以很自然，但背后的决定应当清楚。

除非工具的数据处理规则和任务本身明确允许，否则不要向工具提供密钥、私人线路数据、凭据或无关个人文件。

## 避免模糊要求与“许愿式编程”

“把代码变得更好”“现代化整个项目”“修复所有 bug”“提升性能”或“增加智能编辑器”等要求没有明确终点。如果直接允许工具实现，它只能猜测产品需求、架构、范围和验收标准，这就是“许愿式编程”。

目标仍然模糊时，先让工具只做调查：说明相关所有者、调用路径、测试、测量结果和可选方案，不要立即修改代码。操作者审查证据并补全缺失决定后，再批准一个范围明确的实现。

如果仓库无法回答重要选择，例如文件格式策略、兼容级别、破坏性迁移或新增依赖，应暂停并由人明确决定，不能让工具静默选择。

## 一套实用的协作流程

### 1. 先让工具检查

让工具阅读 `AGENTS.md`，并检查相关实现、测试、构建文件和文档。它应说明当前行为、唯一所有者、受影响的使用方，以及支持修改建议的证据。

### 2. 审查建议方案

允许非简单修改前，确认方案：

- 没有超出请求的组件；
- 复用已有所有者或共享帮助函数；
- 没有增加推测性抽象或重复实现；
- 已说明兼容性、所有权、失效、本地化和源码写回影响；
- 包含现实可行的验证计划。

解释不清时，应要求补充证据或缩小方案。措辞完善的计划不能代替正确的仓库分析。

### 3. 允许工具完成范围明确的修改

不要把无关清理混入同一任务。留意意外的大范围重写、格式化、生成文件、供应商代码、本机路径和新依赖。如果差异超出约定范围，应立即停止并重新评估。

### 4. 亲自检查差异

阅读修改后的代码和文档，不要只看最明显的函数，也要检查边界行为。搜索遗漏的调用方、陈旧字段、重复逻辑、不完整的本地化和错误的缓存假设。

### 5. 验证结果

运行或独立确认相关构建、测试、无界面检查、手工检查、保存重载比较或基准。命令和组件检查清单位于 [`dev_zhcn.md`](dev_zhcn.md) 和 [`AGENTS.md`](../AGENTS.md)。

不能只凭“测试通过”就接受修改，还应看到具体命令、输入、结果及跳过项。如果某项检查无法运行，需要由操作者判断剩余风险是否可接受。

### 6. 记录结果

最终记录应说明修改了什么、为什么修改、实际测试了什么、没有测试什么，以及还有哪些风险。用户行为、开发方式、AI 工作流程或实现状态变化时，应更新对应项目文档。

## 监督功能开发

开发新功能前，先确认该功能确实被要求实现。`TODO.md` 中的条目只记录状态，并不自动授权开发。

接受设计前，确认工具已经：

- 核对官方 BVE 语法，没有发明私有线路语法；
- 找到已有唯一所有者，以及所有需要同步的使用方；
- 考虑强类型 ABI、所有权、有效期、修订、缓存、源码锚点、编码和写回；
- 覆盖适用的解析器/模型、GUI 缓存、表格、二维/三维标记、导航、编辑器、诊断与本地化路径；
- 提出聚焦测试，并更新正确的项目文档。

如果方案先从界面开始，却不能解释底层强类型数据和源码所有权，应特别谨慎。在本项目中，接受新的编辑界面前，应先明确数据与写回契约。

只有在支持与不支持的情况明确、无效输入有清晰错误、关联视图保持一致，并且验证覆盖完整受影响路径时，功能修改才适合接受。

## 监督问题与缺陷修复

修复缺陷时，应先要求具体复现或充分代码证据，并在开始实现前记录预期和实际行为。

让工具追踪第一个错误值或状态，而不是只修补最后显示出的症状，同时检查相邻路径是否共享同一原因。条件允许时，应有一个修改前失败、修改后通过的回归测试或可重复检查。

如果怀疑的问题无法复现，代码也不能证明它存在，可以接受有证据支持的“未复现”结论，不必强求一次重写。

对于编辑和保存缺陷，应在相关时检查 Include 所属语句或引用列表、原编码与行尾、稳定编辑身份，以及保存后重载的强类型快照。对于性能缺陷，应使用相同线路、参数、构建类型和加载配置比较可重复的前后结果。

## 监督 slop-fix

slop-fix 用于移除低质量生成代码或累积代码，例如重复实现、推测性抽象、死字段、无调用方的兼容层、多余包装和隐藏的重复工作。它不是随意改变整个仓库代码风格的理由。

批准 slop-fix 前，应要求一份清点结果：

- 重复、死状态、不必要间接层或已测量成本的具体证据；
- 范围内的所有声明、调用方、测试、构建引用、本地化项，以及 ABI 或序列化使用方；
- 最终保留的唯一实现；
- 修改前的自有生产代码数量与等价实现数量；
- 兼容性和验证清单。

审查时，应拒绝仅缩短名称、删除有用注释、合并行、把复杂度移到生成代码，或在没有至少两个真实现有调用方时引入通用框架的修改。被替代实现和因此失去用途的字段或函数应在同一变更中删除。

slop-fix 通常应减少自有生产代码。如果代码反而增加，工具需要给出能够证明增长合理的正确性或性能测量。测试和文档不计入这项生产代码比较。

完成报告应包含生产代码修改前后数量、移除的等价实现数量、测试和基准的准确输入与结果、跳过项和剩余风险。

## 技术审查重点

即使修改看起来很小，也要检查适用的项目特有风险：

- 公共 ABI：精确版本与结构尺寸、明确所有权、配对释放函数，异常或 STL 类型不能跨越 C 边界。
- 线路源码保真：官方语法、Include 上下文、参数原文、解析顺序、编码、BOM、行尾，以及应用/撤销/保存/重载行为。
- 用户界面：简体中文、英语、日语文本，表格/平面/场景导航，标记可见性与命中优先级，设置持久化。
- 性能：不能逐帧无条件进行 I/O 或重建，不能重复解码或哈希未变化输入，缓存 key 必须完整且有明确失效所有者。
- 依赖：维护状态、Windows 适配、构建与二进制成本、许可证、ABI 影响、打包与迁移风险。
- 分发：除非任务确实需要更新，`LICENSE`、`NOTICE` 和 `THIRD_PARTY_NOTICES.md` 应继续存在并保持不变。

运行时地图数据与编辑命令必须继续使用带版本的强类型 ABI。替代解析器、文本序列化线路传输、回退数据模型或磁盘快照缓存等方案，需要人的明确批准，并且任务本身必须确实要求架构变化。

## 何时暂停或拒绝修改

遇到以下情况时应暂停并重新评估：

- 工具无法解释当前所有者或无法复现问题；
- 实现需要一个从未做出的产品决定；
- 差异涉及无关组件或用户已有修改；
- 意外出现破坏性写入、迁移、新依赖、ABI 变化或大范围架构变化；
- 必要测试失败或被静默跳过；
- 性能结果不一致，或只报告有利结果；
- 所谓清理在没有当前调用方时增加更多抽象；
- 最终说明与实际差异不一致。

AI 可以加快调查和实现，但是否接受修改仍是人的工程决策。相比规模更大却难以审查的结果，应优先选择范围更小、理解充分且验证诚实的修改。

本文档面向使用 AI 编程工具开发 komapedit 的人，说明如何准备任务、监督工具、审查修改，以及判断结果是否可以安全接受。它不是提示词合集，也不应整篇复制给 AI 工具。

AI 工具本身应阅读包含详细仓库规则的 [`AGENTS.md`](../AGENTS.md)。操作工具的人仍然需要对目标、范围、技术决策、验证和最终验收负责。

## AI智能体不是神，它有非常多的局限性
当下的人工智能相关领域充斥着各种炒作与夸大的宣传，这使得相当一部分人认为“AI工具可以根据简短的一句指令就做到任何事情”。但实际上它有非常多的不足点，其中一些足以造成相当大的麻烦。如果你对相关的事实知之甚少，但又计划使用AI编程工具对本项目进行开发，在改动代码之前，你必须知道以下几点：

1. **幻觉：** 基于Transformer架构的大语言模型（LLM）普遍存在一个被称为“幻觉”的严重问题，幻觉在任何模型上都可能存在，即使模型是当今最前沿的版本。这意味模型会生成“看上去没问题，但与事实或指令的偏差相当离谱”的内容，并且不会自我判断该内容是否符合事实或用户需求。
2. **长上下文中的信息丢失：** 当今的前沿模型普遍声称拥有大约100万个令牌（token）的上下文窗口，但是实际输入上下文中的信息变多之后，一些信息会丢失，“哪些信息会丢失”是无法预测的，这意味着模型可能会随着上下文中的信息越来越多，逐渐偏离用户要求和项目规范。一般在一次对话中只建议使用上下文窗口的25%左右，对于工作量特别大的任务，应当拆分成多个步骤，每步与AI智能体进行一次独立的对话。部分AI Agent中会带有上下文压缩功能，一般在对话中触发1次压缩之后，就不建议继续使用此对话继续进行下一轮更改了。
3. **提示词的重要性：** 提示词决定了AI工具会按照的你的指令去做什么。使用尽可能清晰的指令，写清所有规范，避免AI智能体猜测你的需求。

## 应该了解的基础知识
即使使用AI，也并不意味着你可以在对软件开发完全不了解的情况下就能完成想要的更改。以下是一些需要知道的点：
1. 了解软件开发相关的基本知识和工具，可以不安装完整的集成式开发环境（IDE），但最少应该安装本项目需要的构建工具与1个文本编辑器用于手动查看/编辑代码。
2. 至少对C/C++有一定了解，可以没有实际制作项目的经验，但需要知道C/C++的基本语法、各种文件（.h/.cpp等）的用途、相关的各种工具及用途等内容。

## 避免“许愿式编程”

- 不要使用对AI工具没有任何约束的“把代码变得更好”“用xx框架重写整个项目”“修复所有 bug”“提升性能”或“增加某个功能”等模糊要求。如果直接允许智能体实现，它只能猜测产品需求、架构、范围和验收标准，这就是“许愿式编程”。

- 如果程序出现了问题或UI不够美观，不能只说“程序无法正常运行”、“有报错”、“程序突然闪退”、“某个菜单太丑了”，“某个标记不是很对称”。这只会使模型猜测问题点，并且可能导致问题越修越严重。

- 如果需求中有无法自行确定的要素，应该先让智能体只做只读检查，不要立即修改代码（可以使用一些Agent中的“计划”模式）。操作者审查证据并补全缺失决定后，再批准一个范围明确的实现。

- 如果AI对代码的静态检查无法回答重要选择，例如文件格式策略、兼容级别、破坏性迁移或新增依赖，应暂停并由人明确决定，不能让工具静默选择。

提示词模板需要根据实际情况填写内容或选择其中一部分作为实际的输入，不要直接复制未经修改的提示词模板输入AI智能体。

### slop-fix
即使要求严格遵循了项目规范并使用精确指令的提示词，AI编程工具有可能在代码中留下瑕疵，这时便需要进行1次或多次slop-fix修复，使项目可以持续开发。
```
当前项目的开发规范为：AGENTS.md
为防止项目代码偏离要求和规范，下面对当前项目进行开发可持续性（slop-fix）检查与修复，先做只读检查并做计划，在计划中明确列出发现的问题后再执行，若描述的问题不存在，可跳过对应要点：
1.检查是否有大量实现逻辑相同的代码分散在各处。
2.检查是否有已经不使用的字段/函数/变量。
3.检查在功能完全不变的情况下，一些位置是否可以使用更少的代码实现。（注意绝对不能使用删除注释、将原有多行代码合并到同一行等方式缩减行数）
4.检查是否有手动测试无法发现，但在代码层面可见的缺陷。
5.检查是否有可以优化的低效逻辑（频繁的重新加载、读取、计算、生成等）
6.检查是否有可能导致程序执行某些操作时崩溃或彻底卡死的隐患。
7.检查是否存在逻辑混乱或不明的代码。

测试阶段使用真实地图“[Bve地图文件路径]”。如果没有修改代码（没有发现问题），则无需进行测试。

在检查并修正上述问题后，应该做到：
1.代码库更小，更容易维护。但没有可以缩减的位置时不强行压缩代码行数。
2.原有的所有功能与用户操作逻辑不发生变化。
3.程序性能不出现下降。
4.若对应要点存在问题则进行修复，不存在时则不做任何改动，不要为了符合“修复问题”的目标而编造不存在的缺陷并进行重写或修复。
```
## 技术审查重点

即使修改看起来很小，也要检查适用的项目特有风险：

- 公共 ABI：精确版本与结构尺寸、明确所有权、配对释放函数，异常或 STL 类型不能跨越 C 边界。
- 线路源码保真：是否严格遵循Bve官方语法、Include 上下文、参数原文、解析顺序、编码、BOM、行尾，以及应用/撤销/保存/重载行为。
- 用户界面：简体中文、英语、日语文本，表格/平面/场景导航，标记可见性与命中优先级，设置持久化。
- 性能：不能逐帧无条件进行 I/O 或重建，不能重复解码或哈希未变化输入，缓存 key 必须完整且有明确失效所有者。
- 依赖：维护状态、Windows 适配、构建与二进制成本、许可证、ABI 影响、打包与迁移风险。
- 分发：除非任务确实需要更新，`LICENSE`、`NOTICE` 和 `THIRD_PARTY_NOTICES.md` 应继续存在并保持不变。

运行时地图数据与编辑命令必须继续使用带版本的强类型 ABI。替代解析器、文本序列化线路传输、回退数据模型或磁盘快照缓存等方案，需要人的明确批准，并且任务本身必须确实要求架构变化。

## 何时应直接停止智能体
遇到以下情况时应直接停止AI Agent的工作：
1. 改动明显偏离要求，在无关位置改动代码或大规模重写某一模块。
2. 模型输出进入无限循环，反复输出某一段语句或执行某一操作。
3. 改动中出现了C++以外的代码文件：如.py等其它编程语言的源文件。
4. 删除了大量或全部代码，项目明显被破坏至无法恢复原状的程度。

# AI コーディングツールを使った komapedit の開発

[開発者ガイド](dev_jp.md) · [AI ツール向けのリポジトリ規則](../AGENTS.md) · [開発状況](../TODO.md)

このガイドは、AI コーディングツールを使って komapedit を開発する方向けに、タスクの伝え方、作業手順の選び方、変更の確認、成果の検証を説明します。

作業を始める前に、対象機能の操作、C++ の基礎、Windows のビルド環境、差分やテスト結果の読み方を把握しておくと役立ちます。AI の提案を評価し、機能の仕様や完了条件を判断するための知識です。

リポジトリには AI ツール向けの [`AGENTS.md`](../AGENTS.md) と[プロジェクトスキル](../.agents/skills)があり、プロンプトから必要なスキルを直接指定できます。[プロジェクトの知見](../.agents/memories/INDEX.md)は過去の判断を理解する手掛かりになります。現在の実装はソースとテスト、開発状況は [`TODO.md`](../TODO.md) を参照してください。プロジェクト固有のスキルや知見は `.agents` に置き、ユーザー共通のガイドには複数プロジェクトで使う内容を置きます。

## タスクを具体的に伝える

実際の操作と確認可能な結果を基に、次の内容を記載します。

- 現在の動作、または実現したい機能。
- 再現手順と、関連する入力、ログ、スクリーンショット、路線ファイル。
- 変更範囲と、維持する操作性・互換性・性能。
- 期待する結果と完了条件。
- ビルド・テストの範囲、検証に使える路線、手動で行う GUI 確認。

たとえば動作の遅さを改善する場合は、発生する操作、路線の規模、ビルド種別、所要時間を伝えると、原因の特定と結果の評価がしやすくなります。ファイル形式の方針、互換性の移行、公開 ABI、新しい依存関係などの重要な判断がある場合は、まず読み取り専用の調査を依頼し、計画を確認してから実装に進めます。

## 作業手順を選ぶ

リポジトリには、通常の開発、不具合修正、コード保守、ドキュメント作成の 4 種類のワークフローがあります。スキルの明示的な呼び出しに対応したクライアントでは、以下のプロンプト例を使えます。それ以外では、自然言語でタスクを説明し、スキルのパスを指定してください。各ワークフローは、必要に応じてソース編集、テーブル、2D/3D プレビュー、設定、3 言語 UI、検証の専門スキルを組み合わせます。

### 通常の開発

[`komapedit-develop`](../.agents/skills/komapedit-develop/SKILL.md) は、機能の追加や動作の変更に使います。

```text
$komapedit-develop を使用してください。
依頼内容：[機能、対象の操作手順、制約、完了条件]
維持するもの：[互換性、性能、ユーザー操作、ファイル、API]
検証：[Debug ビルド、関連する CTest・ヘッドレス検証、検証用路線、手動 GUI 確認]
```

通常の開発は Debug ビルドで検証します。配布用パッケージ、実行時の依存関係、最適化に関わる問題には Release での検証も加えます。コマンドは[開発者ガイド](dev_jp.md)を参照してください。

### 不具合修正

[`komapedit-fix`](../.agents/skills/komapedit-fix/SKILL.md) は、再現と原因の特定から始め、対象の動作を担当するモジュールで修正します。原因が不明な場合は、先に読み取り専用の診断を依頼できます。修正後は、元の再現手順と関連する回帰テストで結果を確認します。

```text
$komapedit-fix を使用してください。
実際の動作：[症状、ログ、ビルド種別、路線・入力、再現手順]
期待する動作：[正しい動作]
範囲：[診断のみ、または診断と修正]
検証：[元の再現条件と、関連する Debug・Release・ヘッドレス検証]
```

### コード保守（slop-fix）

[`komapedit-slop-fix`](../.agents/skills/komapedit-slop-fix/SKILL.md) は、重複処理、未使用の状態、キャッシュの誤り、潜在的なクラッシュ原因など、根拠のあるコード品質の問題を扱います。まず監査を行い、確認できた問題を、既存の動作と ABI を保って修正します。

```text
$komapedit-slop-fix を使用してください。
範囲：[対象のサブシステム、変更ファイル、またはプロジェクト全体]
まず読み取り専用で監査し、各問題の根拠、影響、修正案、検証方法を示してから、確認できた問題を修正してください。
既存の動作と ABI を維持してください。
検証：厳格な警告を有効にした Debug ビルド、登録済み CTest、関連するヘッドレス検証。性能に関わる場合は、同条件で変更前後を比較してください。
```

監査の結果として、修正が必要な問題が見つからない場合もあります。

### ドキュメント作成

[`komapedit-write-docs`](../.agents/skills/komapedit-write-docs/SKILL.md) は、文書の改訂やコード変更に伴う説明の更新に使います。対象読者、ファイル、言語を指定し、現在のソース、テスト、ビルドスクリプトを根拠にします。

```text
$komapedit-write-docs を使用してください。
内容と読者：[説明する現在の動作・手順と、対象読者]
ファイルと言語：[文書のパス、内容をそろえる英語・簡体字中国語の版]
変更範囲：ドキュメントのみ。
```

[`komapedit-doc-sync-validation`](../.agents/skills/komapedit-doc-sync-validation/SKILL.md) は、変更範囲、言語間の意味の一致、文字コード、リンク、表を確認します。ソースの構成や検証コマンドは、現在のファイル、CMake ターゲット、コマンドラインの入口とも照合します。

### BVE 形式とソース編集を扱う場合

BVE 形式に関わる開発・修正では、[`komapedit-bve-format-compliance`](../.agents/skills/komapedit-bve-format-compliance/SKILL.md) を併用します。対象は[公式情報の基準一覧](../.agents/skills/komapedit-bve-format-compliance/references/official-bve-format-baseline.md)にある Map、Structure List、Signal Aspects List、Sound List、他列車、Scenario の各形式で、読み込み、解析、検証、型付きデータ表現、編集、新規作成、シリアライズ、書き戻しを含みます。

これらのタスクでは、公式ページを基に適合表を作成し、現行構文、旧形式の別名、プロジェクト互換形式、未対応形式を整理してから実装します。公式ページは取得日付きでローカルにキャッシュし、日時が無効、または 30 日を超えている場合は一式を更新します。公式仕様、要件、実装の間に動作を左右する違いがある場合は、ユーザーが対応方針を決めます。

```text
$komapedit-bve-format-compliance と $komapedit-develop（または $komapedit-fix）を併用してください。
形式と要素：[対象のファイル、文、リスト行、セクション、キー]
操作：[読み込み / 検証 / 編集 / 新規作成 / シリアライズ / 書き戻し]
完了条件：[公式の引数形式と意味、保存と再読み込み、有効・無効な入力、元のソース形式の維持]
```

ソース編集には [`komapedit-source-backed-editing`](../.agents/skills/komapedit-source-backed-editing/SKILL.md) を使います。Station、Structure、Signal、Sound、Sound3D のリストをインポート・置換・新規作成する場合や、空リストへの最初の行の追加、行の挿入を扱う場合は、[`komapedit-resource-list-source-editing`](../.agents/skills/komapedit-resource-list-source-editing/SKILL.md) も併用し、形式・編集・保存の流れをまとめて確認します。

## Pi Agent との連携

Pi Agent は、シンプルで効率的なコーディングエージェントです。Pi に実装を任せるには、Pi に直接プロンプトを入力するほか、別のコーディングエージェントに「Pi Agent を呼び出して」と明示するか、[`$collaborate-with-pi`](../.agents/skills/collaborate-with-pi/SKILL.md) を指定します。

調整役のエージェントは、リポジトリを調査して開発計画を `pi-prompts_local.txt` に書き、`pi-agent-here(local).bat` から、画面に表示した Windows Terminal で Pi を起動します。Pi は主な実装、関連テスト、文書の更新を担当します。調整役は進捗を確認し、Pi の完了後に実際の差分をレビューして重要な検証を独立に再実行し、必要に応じて再修正を依頼します。

Pi のセッションに異常が発生した場合は連携を終了し、完了した変更と残作業を報告します。その後の進め方はユーザーが決めます。起動、状態確認、再修正の手順はスキルを参照してください。

## 変更結果を確認する

実際のコード差分をタスクの範囲・完了条件と照合し、変更内容に応じて次の項目を確認します。

- **機能と UI**：対象操作を再実行し、英語・簡体字中国語・日本語の表示、選択状態、マーカー、テーブルと 2D/3D 間の移動、設定の保存を確認します。
- **路線編集**：Include、元の式、文の順序、文字コード、BOM、改行コードの維持を確認し、保存・再読み込み後の内容を比較します。
- **モジュール間のインターフェース**：DLL の変更では、バージョン付きの型付き C ABI、構造体サイズ、データの所有権、対応する解放関数、例外処理を確認します。
- **性能**：同じ路線、パラメーター、ビルド種別、負荷で変更前後を比較し、繰り返しの入出力、毎フレームの再構築、キャッシュの無効化も確認します。
- **依存関係と配布**：Windows・ツールチェーンとの互換性、ライセンスと権利表記、実行時 DLL の配置を確認します。

マップとリソースリストでは、「適用」がメモリ内の作業コピーとプレビューを更新し、「保存」がファイルに書き込みます。「元に戻す」は未保存の変更を破棄し、「再読込」はディスクから読み直します。未保存の変更がある場合は再読込前に確認します。リソースリストの下書きは、先にテーブル内で適用します。シナリオの下書きは「保存」で直接ファイルに書き込みます。この流れを基に、編集から保存までの一連の操作を検証してください。

完了報告には、実行したコマンド、結果、確認済みの失敗を記載し、ビルド、CTest、ヘッドレス検証、手動 GUI 確認を区別します。描画、メニュー、ダイアログ、ドラッグ操作は、実際の画面でも確認してください。作業が範囲を外れた場合、同じ操作で失敗を繰り返す場合、報告と根拠が一致しない場合は、タスクを一旦止め、現在の差分を確認して目的を明確にし直せます。
